# Доступ до API

## Налаштування

`config/secret.js` — локальний серверний файл, виключений з Git. Його формат тепер об’єкт; пароль MongoDB збережено в `DB_PASSWORD`.

- `ADMIN_PASSWORD` — пароль входу в адмінку.
- `ADMIN_TOKEN` — окремий ключ для Postman: `Authorization: Bearer <ADMIN_TOKEN>` або `X-Admin-Token: <ADMIN_TOKEN>`.
- `AUTH_TOKEN_SECRET` — ключ підпису сесій. Його зміна скидає адмінські та робочі сесії.
- `EMAIL` — SMTP-сервер (`host`, `port`, `secure`), облікові дані (`auth.user`, `auth.pass`), відправник (`from`) та одержувач (`to`). Для планової зміни пароля пошти оновіть `EMAIL.auth.pass` і перезапустіть сервер.
- `WORKERS` — масив `{ id, login, name, password, enabled }`. ID має бути унікальним і постійним: він пов’язує помічника з його заявками. Для нового помічника додавайте новий запис. `enabled: false` блокує і новий вхід, і вже видані токени цього помічника після перезапуску сервера.

У локальному `secret.js` уже створено випадкові паролі адміністратора та `worker1`, окремий API-ключ і ключ підпису. Значення можна подивитися або змінити у цьому файлі. Для нового оточення є `config/secret.example.js`. Не копіюйте секрети у фронтенд.

Змінні середовища `ADMIN_PASSWORD`, `ADMIN_TOKEN`, `AUTH_TOKEN_SECRET` мають пріоритет над файлом. Наявний `ADMIN_TOKEN` у `.env` продовжує працювати. Після зміни конфігурації перезапустіть сервер.

## Вхід

Адмін: `POST /backend/auth/login`, JSON `{ "password": "..." }`.

Помічник: `POST /backend/worker/login`, JSON `{ "login": "worker1", "password": "..." }`.

Відповідь: `{ token, user: { id, role, name }, expiresAt }`. Токен чинний 12 годин; передавайте `Authorization: Bearer <token>`. `GET /backend/auth/me` перевіряє адмінську сесію. Після 10 невдалих спроб входу з однієї IP-адреси для відповідної ролі діє пауза до 15 хвилин. Вихід у браузері видаляє локальну сесію; для скидання всіх виданих адмінських/робочих токенів змініть `AUTH_TOKEN_SECRET`.

## Доступи

Без входу доступні:

- `GET /backend/models` і `GET /backend/models/:id`;
- `POST /backend/contactUs`;
- `POST /backend/legalControl`.

Клієнтські `/backend/client/*` зберігають наявну авторизацію. `/client/prices` віддає загальні ціни та записи `prices.clients` / `prices.dropshippers`, які збігаються з `Прізвище Ім’я` поточного клієнта. Чужі персональні ціни не повертаються.

Адмін має повний доступ. Перегляд через `GET /backend/legalControl`, зміна статусу та видалення `legalControl` потребують адмінського токена або API-ключа.

Помічник може:

- переглядати `models`, `components`, `clients`, `services`; у відповідях `services` поле `prices` відсутнє;
- `GET /backend/orders` — тільки власні відкриті заявки;
- `GET /backend/orders/:id` і `PUT /backend/orders/:id` — тільки власна відкрита заявка;
- `POST /backend/orders` — створення заявки. Автор і статус задаються сервером; підміна через тіло запиту ігнорується.

Помічник не може створювати/змінювати клієнтів, змінювати довідники, видаляти заявки чи самостійно змінювати їх статус. Фінансові поля заявок повертаються через API, але інтерфейс працівника приховує роботи й платежі. Вартість посилки доступна для введення. Під час створення/редагування заявки помічником `workerPricing.js` визначає ціну роботи за послугою, моделлю й клієнтом: персональна ціна має пріоритет над ціною дропшипера та загальною. Старі ненульові ціни зберігаються, якщо модель, послуга й клієнт не змінилися. Нулі перераховуються за наявним прайсом; для нової роботи без відповідного прайсу залишається 0. Передана працівником ціна не використовується. Платежі під час створення завжди порожні, під час оновлення не змінюються, навіть якщо працівник надіслав застарілу історію. Адмінське редагування цін і платежів залишається без змін.

## Закриття заявок

`PATCH /backend/orders/:id/status`, JSON `{ "status": "closed" }` або `{ "status": "open" }`. Тільки адмін.

У моделі додано `createdBy: { role, id, name }`, `status`, `closedAt`. Закриття приховує заявку від помічника і блокує його редагування; повторне відкриття повертає доступ. Перевірка власника та стану входить у запит оновлення до БД. Автор не змінюється під час редагування. Старі заявки залишаються в адміністратора; призначення їх помічникам автоматично не виконується. Міграція даних не потрібна.

## Розгортання й перевірка

`server.js` — файл запуску для Node.js / cPanel Passenger; `app.js` — Express-застосунок із маршрутами. Завантажуйте обидва файли. У cPanel файл запуску залишається `server.js`. Запуск виконується також при завантаженні через `require()`, як це робить Passenger. Тести імпортують `app.js`, тому не підключають робочу базу і не запускають основний сервер.

Оновіть серверний код, зберігши чинні приватні `config/secret.js` та `.env`. Не замінюйте їх локальними секретами. Потрібні поля конфігурації звірте з шаблоном та `DEPLOYMENT.md`, після перевірок перезапустіть Node.js. Старий формат `secret.js`, який експортує лише рядок пароля БД, підтримується підключенням MongoDB, але для нового входу потрібні поля конфігурації вище. Одночасно завантажте нову адмінку: старий фронтенд не передає токен.

`node --test tests/access.test.js` або `npm test` перевіряє маршрути через локальний HTTP-сервер із підміною моделей; робоча MongoDB й SMTP не викликаються.
